# Privacy and security

What MangaPixer keeps to itself, what it can send when an admin allows it, and how to report a vulnerability.

- **No telemetry, analytics or phone-home.** Fonts and icons are bundled and served by your own server, never from a CDN.
- **Two optional internet features, both off by default and switched on only by an admin:** the Update Checker and fetching series information from the allowed sites - MangaUpdates, the Grand Comics Database (comics), MangaDex (volume covers), AniList (chapters per volume) and Wikipedia (volume lists) (see [What leaves your server](#what-leaves-your-server)).
- **Logs never contain paths or titles**, only IDs, counts, timings and sanitized error codes. Reader-facing API responses never contain filesystem paths.
- **Source media is read-only**, enforced by the code and by the `:ro` mounts.
- **No default credentials.** The first admin is created by you on the setup screen, and that endpoint refuses once any user exists.
- **API tokens** (1.33.0) are created only by an admin, read only the metadata export - and, only when the admin ticks it (1.36.0), may request a full library scan - and nothing else, and are stored as a SHA-256 fingerprint - the token itself is shown once and never written to the database or the logs (see [API tokens](api-tokens.md)).
- Session cookies use ASP.NET Core Data Protection; the keys live in `<DataRoot>/keys`, so treat the data volume as sensitive.

## What leaves your server

Out of the box, nothing: MangaPixer makes no internet requests until an admin turns something on. The **Update Checker** asks GitHub once a day whether a newer release exists. **Fetch series information from the web** (account menu > Metadata Manager, after a consent text, and per library) lets an admin look a folder up on [MangaUpdates](https://www.mangaupdates.com): only the search text the admin confirms in the Identify dialog, MangaUpdates record numbers, a fixed list of types to leave out (when **Hide doujinshi & novels** is ticked) and the fixed `User-Agent` (see [User-Agent](#user-agent)) are sent, only to `api.mangaupdates.com` and `cdn.mangaupdates.com`, and only when an admin presses Search, Look up, Preview, Link, Accept or Refresh. File paths, your file list, user accounts and reading progress are never sent. Fetched data and cover art are stored on your server and served from it, so readers' browsers never contact MangaUpdates. **Automatic matching** is a separate switch with its own consent text, off by default: when an admin turns it on, libraries that fetch from the web are matched in the background, so the cleaned name of each new series folder (or of an archive that is its own work: in a collection or artist's folder, or loose next to other folders; *from 1.34.0* also each work inside a folder an admin marked **Collection about** a linked series, then searched as `<series> dj - <title>` with the series' MangaUpdates title - never a folder or file name - in front) is sent without anyone reviewing it first (and, when the first page of results is a tie or has nothing close enough, the second page of that same search is read), and linked series are refreshed by their MangaUpdates number. When two records tie on the title for a folder of volumes or a one-shot, it may also download those two records' cover images from `cdn.mangaupdates.com` to compare them with the folder's own cover thumbnail on your server (**Compare covers**, part of Automatic matching; the downloaded covers are deleted right after, and nothing from your library is sent with them). It uses the same hosts and the same daily request budget, at most one request per second, and never looks inside a folder marked **Don't match**. The cleaned name of a folder that is still waiting can be sent again: an unmatched one after 30, 90 and 180 days, and one in **Needs review** once after an update changes how matches are scored (never one an admin linked, confirmed or marked **Don't match**); this is the same request to the same site. `Metadata__NetworkDisabled=true` switches all of this off regardless of the admin settings. Details: [Series information](series-information.md#what-is-sent).

Series data fetched from the web is provided by [MangaUpdates](https://www.mangaupdates.com) and credited to it wherever it is shown.

### Allowed sites and AniList

*New in 1.28.0.* MangaPixer contacts only the **allowed sites** listed in Metadata Manager > Settings: MangaUpdates, the [Grand Comics Database](https://www.comics.org) (1.32.0, see below), [MangaDex](https://mangadex.org) (1.29.0, see below), for chapters per volume [AniList](https://anilist.co), and [Wikipedia](https://en.wikipedia.org) (1.32.0, see below). An admin can remove any of them; a removed site gets no request of any kind. AniList is asked when an admin presses **Get chapters per volume from AniList** or **Chapters per volume (AniList)** in the Missing report, and - from 1.29.0, with Automatic matching on - in the background for a linked series that MangaDex gives no volume list for; only for libraries whose **Fetch** switch is on, and never to match a folder: MangaPixer sends the AniList record number when it is known (entered by an admin, stored, or taken from the linked MangaDex record's own AniList link), otherwise the MangaUpdates title of a series that is already linked (never a folder or file name), a fixed "manga, not novels" filter and the fixed `User-Agent`, only to `graphql.anilist.co`. It stores the matching entry's volume and chapter totals on your server, counts every request in the same daily budget, sends at most one request per second, and waits when AniList asks it to slow down. When an update changes the allowed sites or what is sent, fetching stays off until an admin accepts the new consent text ([After an update: accept again](series-information.md#after-an-update-accept-again)). AniList data is credited to AniList where it is shown.

### MangaDex: volume covers and volume lists

*New in 1.29.0.* [MangaDex](https://mangadex.org) is used only as a companion of a series that is already linked to a MangaUpdates record, for that series' volume -> chapter list and its volume covers; it is never used to identify or match a folder. MangaPixer sends it only the title or an associated title of the linked MangaUpdates record (never a folder or file name), MangaDex record numbers, a fixed content-rating list, your preferred and the series' original cover language as a filter (your preferred language also for the volume -> chapter list, to learn which chapters are released in it), and the fixed `User-Agent` (no `Via` header, no cookies, nothing that identifies your server), only to `api.mangadex.org` and `uploads.mangadex.org`. A MangaDex record is used only when its own MangaUpdates link names the linked record, or when an admin chose it (**Change MangaDex match…**). Cover images are downloaded by the record number and file name MangaDex returned (the 512-pixel version), re-encoded and hashed by MangaPixer's media worker and stored in the data root; readers' browsers never contact MangaDex. *From 1.33.0* MangaPixer also keeps the official-source links listed in the same MangaDex record answer (the official original-language and English pages, and the BookWalker, Amazon, ebookjapan and CDJapan store pages) for the [metadata export](metadata-export.md); it never requests those addresses itself, and reading them adds no request.

With **Automatic matching** on and **Volume covers from the web** on (Metadata Manager > Settings > Volume covers; on by default; `Metadata__AutoMatch__VolumeCovers=false` switches it off regardless of the setting), this happens in the background for every linked series: find its MangaDex record, read its volume list (in all languages and in your preferred language) and its volume covers in the two languages, download the covers of volume 1 and of the volumes the folder holds (as volume files, as all of their chapters by MangaDex's volume list, or as an estimated `~ Volume N` stack of the Volumes view) - or, when MangaDex lists no volume 1 cover (webtoons, for example), its main cover - and look again on the series' refresh schedule until a cover in your preferred language appears. Without Automatic matching, MangaDex is contacted only when an admin asks (**Refresh**, **Change MangaDex match…**). Everything counts in the same daily budget, at most one request per second, and pauses while MangaDex asks to slow down. Nothing inside a folder marked **Don't match** is looked up. Removing MangaDex from the allowed sites stops every request to it; covers already stored stay and keep being shown until you use **Delete stored volume covers**. Logs record IDs, counts, status codes and timings only. Cover images and volume data come from MangaDex, credited under its setting in Metadata Manager.

### Grand Comics Database: comics and graphic novels

*New in 1.32.0.* The [Grand Comics Database](https://www.comics.org) (GCD) is the site MangaPixer asks about comics and graphic novels - works with a comics signal (for example a folder declared Comic or Graphic novel, a folder below a Comics / BD folder, comic-issue or album numbering together with another comics sign, or a comics link inside ComicInfo) - and any work an admin chooses to search there in Identify. It is sent only the search text the admin confirms (with **Automatic matching** on, also the cleaned name of a new comics folder - first to GCD, and to MangaUpdates only when GCD finds nothing close), a start year when the name has one, GCD record numbers and the fixed `User-Agent`; no account or key, nothing that identifies your server, only to `www.comics.org` and `files1.comics.org`. GCD's cover thumbnails are shown only while you choose, and may be compared in memory with a folder's own cover; they are never stored as covers - comic files keep their own cover. GCD answers anonymous users slowly, so MangaPixer sends it at most 25 requests an hour, inside the same daily budget. Comics data is credited "Grand Comics Database (comics.org), CC BY-SA 4.0" where it is shown.

### Wikipedia: volume lists

*New in 1.32.0.* [Wikipedia](https://en.wikipedia.org) is used only as a companion of a series already linked to a MangaUpdates record, to read which chapters make up each volume - with each volume's English release date and ISBN - from its English "List of ... chapters" page, where MangaDex's list has gaps; it is never used to identify or match a folder. MangaPixer sends only the linked MangaUpdates record number (to [Wikidata](https://www.wikidata.org), to find the English article linked to it), the page titles found that way or the linked series' MangaUpdates title (never a folder or file name), fixed query parameters and the fixed `User-Agent`, only to `en.wikipedia.org` and `www.wikidata.org`, one request at a time. Only volume and chapter numbers, dates, ISBNs, the page title and its revision are kept, credited to Wikipedia with a link. Without Automatic matching it is contacted only when an admin asks; in the background it runs only while **Volume covers from the web** is on.

### API tokens

*New in 1.33.0.* An admin can create **API tokens** in Administration so another program - MangaList - can read the metadata export (`/api/v1/export/`). A token can only read that export: it is refused for anything but reading requests, and sent to any other page it is ignored as if it were absent. *From 1.36.0* an admin can also tick **Request library scans** for a token: it may then ask for a full scan of a library (`POST /api/v1/export/libraries/{id}/scan`, at most once per library every 5 minutes) - the same local scan as **Scan now**, which changes no files, links or settings and sends nothing to the internet. That one address accepts only tokens, never a browser sign-in. Each started scan is recorded in the Audit trail. It works only while the admin who created it is an active admin, and until it is revoked or expires. MangaPixer stores only a SHA-256 fingerprint of each token; the token is shown once, never logged (log lines name a token by its public id), and never sent anywhere. Use HTTPS when the program reaches MangaPixer from outside your home network. Details: [API tokens](api-tokens.md).

### User-Agent

*New in 1.32.0.* Every request to an allowed site carries the same `User-Agent`: `MangaPixer/<version> (+https://github.com/dixit92/mangapixer)` - the product, its version and the project page, as MangaDex and Wikimedia ask. It is identical on every MangaPixer server of that version, so it does not identify yours. (Before 1.32.0 it was `MangaPixer-Metadata`.) The Update Checker keeps its own generic `User-Agent` for GitHub.

To report a vulnerability, see [SECURITY.md](../SECURITY.md).
